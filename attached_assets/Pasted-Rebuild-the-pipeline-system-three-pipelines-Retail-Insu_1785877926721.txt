Rebuild the pipeline system: three pipelines (Retail, Insurance, Project), with stage-exit tasks performed INLINE on the pipeline kanban cards — not in the lead profile. Retail and Insurance converge into Project. Several transitions auto-advance on system events instead of manual tasks.

=== CORE MODEL ===

1. Stage convention: a stage name describes the lead's CURRENT true state; the inline task on the card is the action that EXITS the stage. Never name a stage after work not yet done.

2. Schema:
   - pipeline_stages (seeded config): id, pipeline ('retail'|'insurance'|'project'), key, label, sortOrder, exitTask (jsonb: { type, config }), autoAdvance (jsonb nullable: { eventType, outcomeRules }), isLoopStage (bool), isTerminal (bool).
   - leads gain: pipeline, stageKey, stageEnteredAt, loopNextActionAt (nullable), lossReason (nullable), sourcePipeline (nullable — set at Project entry: 'retail'|'insurance').
   - stage_transitions (audit): id, leadId, fromStage, toStage, trigger ('task'|'auto_event'|'manual_move'), taskPayload (jsonb), userId nullable, eventId nullable, createdAt. Every transition writes a row and a claim_event/lead_event.

3. Exit task widget types (rendered on the kanban card):
   - assign_user: dropdown of team members filtered by role
   - datetime: date/time picker
   - date_range: start/end picker
   - confirm: single-tap confirm button
   - money_confirm: $ confirm button (records amount + date)
   - outcome_buttons: 2-3 buttons, each mapping to a target stage
   - button_link: button that routes to another surface (proposal builder, Claim Hub) — stage exits via auto-advance event, not the click
   - fields: 1-3 small inline fields + save (e.g., claim number + filing date)
   - upload: file upload (signed contract)
   All widgets submit without leaving the pipeline view; card animates to the next column on success.

4. Auto-advance: a worker listens for the named events and advances matching leads, writing stage_transitions with trigger auto_event. Card shows a status badge ("Awaiting e-sign", "Awaiting field sync") instead of a task widget while waiting.

5. Loop stages (isLoopStage): require loopNextActionAt on entry; cards sort by it within the column; cards past their date get an amber "overdue" border; cards >14 days in a loop stage get a red age badge showing days-in-stage.

=== RETAIL PIPELINE ===
Stages in order (key — label — exit task / auto):
1. pin_dropped — Pin Dropped — assign_user (sales rep)
2. appt_needed — Appt. Needed — datetime (schedule appt)
3. appt_scheduled — Appt. Scheduled — confirm ("Confirm Appt"); confirmed state shows as checkmark on card, not a separate stage
4. appt_complete — Appt. Complete — button_link → proposal builder; auto-advance on event proposal_generated
5. proposal_provided — Proposal Provided — outcome_buttons: Won → contract_pending / Follow-Up → follow_up / Lost → archived_lost
6. follow_up — Follow-Up — LOOP STAGE: datetime (next follow-up, sets loopNextActionAt) + same outcome_buttons as stage 5
7. contract_pending — Contract Pending — button_link → contract generation; auto-advance on event contract_signed (e-sign) OR upload widget (wet-signed)
8. contract_signed — Contract Signed — money_confirm ("Collect Deposit")
9. deposit_received — Deposit Received — assign_user (project manager) → on completion, CONVERGE: lead moves to Project pipeline stage pm_handoff, sourcePipeline='retail'
10. archived_lost — Archived (Lost) — TERMINAL; entering requires lossReason dropdown: price | timing | competitor | no_response | other
