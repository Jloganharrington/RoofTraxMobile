TEAM CALENDAR — BUILD ORDER

Scheduling already exists in this repo, fragmented across four incompatible
shapes. This order unifies the READ side into a calendar and fixes the one
source that is genuinely unusable. It does NOT introduce a new appointments
table — that consolidation decision comes after two real lifecycles have run.

Current state, verified:
  inspections.scheduledFor        real timestamptz column, WORKING booking flow
                                  (POST notify-schedule, PATCH /schedule,
                                  GET /inspections/scheduled consumed by mobile)
  pins.adjusterMeetingDate        real timestamptz column, set via the insurance
                                  PATCH, no calendar surface
  pins.retailData.appointmentDate STRING inside a jsonb blob — not queryable,
                                  not sortable, cannot drive a calendar
  phase1_scheduled                a pipeline stage with NOTHING that books it

STANDING BOUNDARIES: never modify artifacts/mobile/; never hand-edit generated
client files (edit lib/api-spec/openapi.yaml, regenerate); never hand-write a
query key for a generated hook; server enforcement authoritative; integer cents.
STOP at each ▶ CHECKPOINT, paste real output, PUSH, wait for confirmation.

pins.retailData.appointmentDate is a free-text string inside jsonb. It cannot
be indexed, range-queried, or ordered, so a calendar would have to unpack every
pin in the company to find next week's appointments. Promote it.

1a. Migration 037 (verify 037 is free — 036 is the latest), on pins:
      appointment_at            timestamptz NULL
      appointment_assigned_to   varchar NULL REFERENCES users(id)
      appointment_status        varchar NULL  -- scheduled | completed | canceled | no_show
                                              -- const array, validated server-side
    Index on (company_id, appointment_at).

1b. Backfill from retailData.appointmentDate inside the same migration.
    Values are dirty free text — parse defensively, SKIP anything that isn't a
    resolvable date rather than inserting a garbage timestamp or epoch zero.
    Must be idempotent; state how you guaranteed it.
    Do NOT delete retailData.appointmentDate — leave it as a read-only legacy
    source, same treatment as the legacy money columns.

1c. Booking path: extend the existing pin PATCH surface (or add a dedicated
    endpoint — your call, say which) so a retail appointment can be set,
    reassigned, rescheduled, and marked completed/canceled/no-show.
    Writes follow the same rule as pin edits. Completing an appointment
    SERVER-STAMPS the status change; never accept a client-supplied timestamp.

║ STEP 3 [LOCKED] — UNIFIED CALENDAR FEED                   ║
╚═══════════════════════════════════════════════════════════╝
One endpoint, four sources, one normalised item shape. This is a READ layer —
it creates no new storage.

3a. GET /calendar?from=&to=  (openapi-first, then regenerate)

    Sources to union:
      inspection_phase1   inspections.scheduledFor where phase='preliminary'
      inspection_phase2   inspections.scheduledFor where phase='forensic'
      retail_appointment  pins.appointment_at            (from step 1)
      adjuster_meeting    pins.adjusterMeetingDate

    Normalised item — every source maps to this, no source-specific fields
    leaking into the response:
      id            stable, source-prefixed (e.g. "insp:<uuid>", "pin:<uuid>")
      type          one of the four above
      startsAt      ISO timestamp
      endsAt        null for now — no source carries duration. Do NOT invent one.
      title         human-readable
      propertyAddress
      assignedUserId + assignedUserName   (null where the source has no assignee)
      pinId, inspectionId  (nullable, for deep-linking)
      status        where the source has one; null otherwise

3b. SCOPING [LOCKED]. Mirror the rule /inspections/scheduled already uses —
    do not invent a second visibility model:
      field_rep  → only items assigned to them
      manager+   → the whole company
    Resolve the role from the DB profile row. A field_rep must not be able to
    widen scope through any request parameter.

3c. Company-scope every source. ⚠ Both pins and inspections carry company_id
    directly — use it. Do not scope through a join where a direct column exists.

3d. Require from/to and cap the range (e.g. 90 days). An unbounded calendar
    query over a company with years of history is a table scan on every load.
    Reject out-of-range with 400 rather than silently clamping.
