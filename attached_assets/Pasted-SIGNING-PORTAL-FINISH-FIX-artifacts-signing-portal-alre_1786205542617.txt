║ STEP 2 [LOCKED] — THE SIGNATURE MUST BIND TO THE DOCUMENT ║
╚═══════════════════════════════════════════════════════════╝
This is the step that decides whether the signature is defensible.

2a. The customer MUST see the rendered contract document before signing, in
    the same session, and the signature control must not be reachable until
    they have. A signature attached to a document the signer never viewed is
    the weakest possible position in a dispute.
    Verify the current flow enforces this. If the sign action is available
    while the document is unviewed or ungenerated, fix it.

2b. Bind the signature to the exact bytes signed. The sign request must carry
    the document_sha256 the customer viewed, and the server must reject the
    signature if it does not match the stored hash — 409, not a silent
    accept. This closes the window where selections change between document
    generation and signature.
    Report whether contractPortal.ts already does this; if not, add it.

2c. Server-stamp everything evidentiary. customer_signed_at must be set
    server-side, never from the client. Same for any IP or user-agent capture
    if you add it (recommended — it strengthens the record; say if you do).

2d. Re-signing must be impossible. A contract already signed rejects a second
    signature with 409. Verify.

╔═══════════════════════════════════════════════════════════╗
║ STEP 3 [REASONING OK] — THE THREE ARRIVAL STATES          ║
╚═══════════════════════════════════════════════════════════╝
The portal must handle arriving in any of these without confusion:

  NOTHING SELECTED — customer self-serving. Full flow: select each package,
      review the document, sign.
  ALREADY SELECTED — a rep made the selections at the kitchen table and
      handed over the phone. Do NOT re-ask. Show what was chosen, allow
      changing it, and go straight to review-and-sign.
  ALREADY SIGNED — read-only confirmation with the executed document
      downloadable. No selection controls, no signature pad.

Also handle: invalid or expired code, and a voided contract. Both need a
plain-language dead end — "this link is no longer active, please contact
{company}" — never a stack trace, a blank screen, or a JSON error.

╔═══════════════════════════════════════════════════════════╗
║ STEP 4 [LOCKED] — PRICE CLARITY                           ║
╚═══════════════════════════════════════════════════════════╝
The customer is agreeing to pay money. Ambiguity here is the thing that
generates disputes, and the numbers must reconcile on screen.

4a. Every upgrade shows its per-unit rate AND the extended amount:
    "+$85.00 per square × 28 squares = +$2,380.00". Never a bare delta the
    customer has to multiply, and never an extended figure with no derivation.

4b. The base tier must be unmistakably free — "Included, no additional cost"
    — not "+$0.00", which reads as a charge.

4c. State out-of-pocket separately from contract total, and label who pays
    what. The customer cares about ONE number: deductible + betterments.
    The total contract value is context, not their bill. Do not let the
    larger number be the visually dominant one.

4d. The on-screen figures must equal the PDF. If they can diverge, that is a
    dispute waiting to happen — confirm both derive from the same server
    values, not from client-side recomputation.
