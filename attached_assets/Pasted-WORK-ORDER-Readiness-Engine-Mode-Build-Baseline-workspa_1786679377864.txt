STEP 2 — One engine
lib/protocol becomes the sole authority. Every rule from readiness, preflight, and lint that is genuinely a completeness rule moves into rules.ts as a Deficiency or SoftFlag. Content-quality rules stay in lint if that's what Step 1 shows them to be.

Two requirements on the rules themselves:

Every deficiency needs a human sentence and a machine code. The shape already has both — { stage, code, message }. message is what a contractor reads; code is what the UI keys off. A message like "Wide photo missing for the north elevation" is the product teaching the methodology. "ELEVATION_PHOTO_MISSING" is not.

Every deficiency needs a resolution path. Add a resolution field naming what the contractor does about it: capture it in the app, upload it, or acknowledge it as unavailable. That field is what makes the same engine work for both capture paths.

Keep the package dependency-free — it's consumed by the API, the web app, and the mobile app, and it must stay portable.

STEP 3 — Applicability
Wire applicableSteps(flags) in. A roof-only claim should never be told its siding documentation is incomplete, and right now nothing consults the applicability model at all.

Damage flags come from the inspection record. Report what sets them today and whether the upload path can set them from intake — the contractor selecting "roof and siding" at Stage 3 is the natural source.
