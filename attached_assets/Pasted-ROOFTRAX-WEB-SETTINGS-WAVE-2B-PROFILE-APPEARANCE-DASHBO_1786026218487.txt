TASK D1 [LOCKED] — Dashboard tab: widget visibility + order
════════════════════════════════════════════════════════════
Layout shape (already migrated in P2): { hidden: string[], order: string[] }
— widget KEYS only, never titles.

Server rule — this is the security-relevant part, get it exact:
GET /dashboard/manifest applies the stored layout AFTER selectWidgetsFor().
The capability-resolved set remains the universe; layout is a view on it.
  - hidden: subtracts keys from the resolved set. Keys not in the resolved
    set are ignored (they subtract nothing, they add nothing).
  - order: sorts the remaining resolved keys. Keys not in the resolved set
    are dropped. Resolved widgets NOT listed in order append AFTER the
    ordered ones, in catalog order — this is required so a newly shipped
    widget appears for users with saved layouts instead of vanishing.
  - Stale/unknown keys anywhere in the layout are ignored silently — a
    catalog change must never 500 a manifest request.
  - A layout can never ADD a widget. There is no code path where a key in
    the stored layout reaches the response unless the resolver granted it.

API (openapi-first): PATCH /dashboard/layout (validated {hidden, order},
self-only) and DELETE /dashboard/layout (nulls the column = restore
defaults). Server-side validation: arrays of strings, sane length cap
(e.g. 50), no other fields.

UI — Dashboard tab: list the user's GRANTED widgets (source the list from
the manifest response — never from WIDGET_CATALOG directly, the manifest IS
their universe), each with a visibility toggle and up/down reorder buttons.
No drag-and-drop unless something already installed makes it trivial.
"Restore defaults" calls the DELETE. Changes reflect on the dashboard
without a full reload (invalidate the manifest query on save).

VERIFY (paste real output):

  - As field_rep, PATCH a layout with "action_required" in BOTH hidden and
