MONEY IS INTEGER CENTS. Not varchar, not float, not numeric.

Type vocabulary — export as a const array from the schema file, validate
server-side against it (same pattern as TEMPLATE_USE_CASES):
    deposit, acv, betterment, supplement, final, rcv_holdback,
    deductible, other

1b [LOCKED] Backfill inside migration 023, from the legacy pins columns:
    depositAmount      → 'deposit',    date = depositDate ?? created_at
    acvAmount          → 'acv'
    supplementAmount   → 'supplement'
    finalPaymentAmount → 'final'
Rules:
  - Legacy strings are dirty: may contain "$", commas, whitespace, or be
    non-numeric. Parse defensively; SKIP rather than insert garbage or zero.
  - Skip null and zero amounts entirely.
  - Convert to cents by multiplying by 100 and ROUNDING. Never truncate.
    1234.56 must become exactly 123456, not 123455. Floating-point drift here
    silently corrupts every downstream total.
  - MUST be idempotent — re-running must not duplicate. State how you
    guaranteed that.
  - Do NOT delete or modify the legacy pins columns. They stay as a read-only
    backfill source; retiring them is a later decision.

1c [LOCKED] API (openapi-first):
    GET    /pins/:pinId/payments
    POST   /pins/:pinId/payments
    PATCH  /payments/:paymentId
    DELETE /payments/:paymentId
Authorization via roleRank from @workspace/authz. Reading follows the same
rule as reading the lead. Create/update/delete is manager+ — field reps must
not write financial records. Verify pin↔company on EVERY endpoint including
PATCH and DELETE by paymentId.

1d [LOCKED] THE FIVE BUG FIXES — do not reintroduce:
  (i)   IDOR ON UPDATE. company_id and pin_id must NEVER be client-settable on
        PATCH. Strip both from any payload; re-verify the existing row's
        company matches the caller before writing. Reassigning a payment to
        another lead is the attack.
  (ii)  IDEMPOTENCY. No create path may assume exactly-once delivery. Becomes
        critical in step 2 when marking an invoice paid writes a ledger row.
  (iii) NO BYPASS ROUTE. Money must not be writable through any other endpoint.
        Inspect the generic pin PATCH handler: if it accepts contractAmount /
        depositAmount / acvAmount / etc., that is a second write path that will
        diverge from the ledger. REPORT what you found and how you handled it.
  (iv)  CONSISTENT COHORT. Aggregates must sum over one consistently-scoped
        set. Mixing "all company payments" with "payments for a filtered lead
        set" produced nonsensical negative balances previously.
  (v)   STALE WRITE ON CONTEXT SWITCH. Any debounced money input MUST cancel
        its pending write when the user switches leads, or the value lands on
        the wrong record.

1e [REASONING OK] UI — payments section of the Lead Profile Financials tab:
list with type badge, date, amount, delete; "Total Payments" summary; add/edit.
Display dollars, store and transmit cents — format at the boundary only, never

"12500") and convert once, at the edge.
Do NOT build invoices, expenses, commissions, or P&L here.

4a [LOCKED] Port computeLeadFinancials from the reference's financeMath.ts
into a shared server module, CONVERTED TO CENTS (the reference does string
math — do not carry that across). Preserve these decisions exactly:
    expectedTotal   = leadType === insurance
                        ? max(contractAmount, approvedRcvAmount)
                        : contractAmount
    collectedTotal  = sum of ALL ledger payments for the pin
    deductibleCollected = sum of payments where type = 'deductible'
    vendorExpenses  = sum of vendor_expenses for the pin
                      (materialOrderTotal is deliberately EXCLUDED — it
                       double-counts against vendor invoices)
    totalCosts      = vendorExpenses + salesCommission + pmCommission
                      + leadAcquisitionCost + referralFee
    netProfit       = collectedTotal − totalCosts
    cashMarginPct       = collected > 0 ? (collected − costs)/collected × 100 : 0
    projectedMarginPct  = expected  > 0 ? (expected  − costs)/expected  × 100 : 0
Both margins are required. Cash-only made in-progress jobs look unprofitable —
that is why the pair exists.

This module is the SINGLE SOURCE OF TRUTH. The Financials tab, the Insurance
tab, and any later CSV export or company rollup must all call it. Do not
recompute P&L anywhere else — that is how the dashboard and the lead page
start disagreeing.
