═══════════════════════════════════════════════════════════
HARD RULES FOR ALL SIX
═══════════════════════════════════════════════════════════
1. requireWidgetCapability('<key>') as FIRST middleware on every data
   endpoint. See the action_required / knock_to_lead endpoints in
   artifacts/api-server/src/routes/dashboard.ts as the reference pattern.
2. Company-scope every query by req.user.companyId.
3. Read stage vocabulary from SERVER_STAGES_ARRAY in
   artifacts/api-server/src/lib/pipelineStages.ts. NEVER hardcode stage key
   lists — the insurance pipeline gained six stages recently and hardcoded
   lists would already be wrong.
4. Do NOT create new tables or columns.
5. Cap any list-returning endpoint and report {total, capped} honestly.
   Never silently truncate.

⚠ TENANCY LANDMINE — read before writing any query:
   stage_transitions has NO companyId column. It has only leadId (a pin id).
   Any query touching stage_transitions MUST join through pins and filter on
   pins.companyId. A query that filters stage_transitions alone will return
   other companies' activity. This is the single most likely way to introduce
   a cross-tenant leak in this batch — treat it as the thing to get right.
   claim_events DOES have companyId; scope it directly.

SCOPING DECISION — applies to B2 (pending_inspections, claim_blockers)
═══════════════════════════════════════════════════════════
Unlike every widget built so far, these two are gated by DEPARTMENT and
WORKFLOW, not by role — so a field_rep can see them. That means data scope
must be decided, not assumed.

LOCKED RULE: field_rep sees ONLY their own; manager+ sees company-wide.
This mirrors how /activity-stats already clamps field_rep to scope='own'.
Resolve the actor's role from the DB profile row and clamp server-side. A
field_rep must never be able to widen scope via any request parameter.

"Their own" means:
  - pending_inspections → inspections.inspectorUserId = actor
  - claim_blockers      → the owning rep of the underlying pin (pins.userId)

  they're a field_rep, and it's workflow-gated rather than manager-gated.

GROUP B3 — recent_activity (all users)  [REASONING OK]
═══════════════════════════════════════════════════════════
GOAL: a scrolling log of what's happening that's relevant to this user.

DATA — two sources, merge them:
  - claim_events (inspectionId, companyId, eventType from CLAIM_EVENT_TYPES,
    payload jsonb, actorId, createdAt). Has companyId — scope directly.
  - stage_transitions (leadId, fromStage, toStage, trigger from
    STAGE_TRANSITION_TRIGGERS, taskPayload, userId, createdAt). NO companyId
    — MUST join through pins and filter pins.companyId. See the tenancy
    landmine above.

Requirements:
  - Merge both sources into one reverse-chronological feed with a consistent
    item shape. Cap it (e.g. 30) and report total.
  - Resolve actor names — a feed of user IDs is useless. Note that
    stage_transitions.userId is NULL for auto_event triggers; render those as
    a system action, not as "Unknown user".
  - Use the enum vocabularies (CLAIM_EVENT_TYPES, STAGE_TRANSITION_TRIGGERS)
    to produce human-readable text. Do not print raw enum keys at the user.
  - Scope: everyone sees company activity (this is a "what's happening on the
    team" feed, matching its all-users gating). Do NOT include anything a
    role shouldn't see — if any claim_event payload carries sensitive detail,
    surface the event type, not the payload contents.
