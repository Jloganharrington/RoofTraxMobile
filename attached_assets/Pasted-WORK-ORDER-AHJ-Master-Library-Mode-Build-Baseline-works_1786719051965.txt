STEP 2 — Master schema
ahj_master_packs, no company_id:

Unique on (state, county, pack_type, version). State and county are structured columns — the coverage list depends on them and parsing at read time defeats the purpose.

ahj_master_adoptions: company_id, master_pack_id, adopted_pack_id, adopted_at. This is what lets a code-cycle update report who is behind.

Reconcile ahj_coverage per Step 1 — either extend it as the coverage projection over master packs, or fold it in and keep the name.

STEP 3 — Promotion
POST /ahj-master/promote, super_admin only. Promotion is RoofTrax publishing verified research, not a tenant action.

Copies items only. Never corpus_chunks, never code_sources, never verbatim code text. A tenant's licensed copy of a code book stays inside that tenant; what goes up is citation, edition, provision summary, classification, factual trigger, and scope connection — research output, not the source document.

Write a test that fails if the promoted payload contains a corpus reference or verbatim source text. This is the licensing boundary and it should be enforced by a test rather than by care.

Reject promotion when any item is unverified. Items are born unverified by design, and promotion propagates to every future tenant in that county — the review gate exists precisely for this moment.

If a master pack already exists for (state, county, pack_type), create version N+1 and set superseded_by_id on the prior version. Never mutate a published version.

STEP 4 — Coverage list and adoption
GET /ahj-master/coverage — the browsable list for signup step 7. Returns state, county, label, code cycle, and status per jurisdiction. Unauthenticated and rate-limited, returning status only, never pack contents. It doubles as a marketing surface, so it should be safe to expose publicly.

GET /ahj-master/coverage?state=&county= — single lookup, same shape.

POST /companies/:companyId/ahj-packs/adopt — copies the current master version into a company-scoped ahj_packs row and records the adoption. This belongs inside the provisioning transaction so a new tenant lands with coverage already in place.

STEP 5 — Requests
POST /ahj-master/requests — the "Don't see your AHJ? Request it" path. Writes to waitlist_entries if that table fits, or its own table if not; Step 1's report decides.

Admin view listing requested jurisdictions ranked by request count. That ranking is the demand map that tells you which county to build next.

STEP 6 — Staleness
GET /ahj-master/adoptions/stale — tenants on a superseded version, grouped by jurisdiction. Report-only; the refresh action is a later decision. This is what turns "AHJ packs refreshed on code-cycle adoption" from a checklist line into something the system surfaces.
