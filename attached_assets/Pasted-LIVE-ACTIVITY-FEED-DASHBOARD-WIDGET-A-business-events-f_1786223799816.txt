build it as a separate widget.

║ STEP 1 [LOCKED] — CLAIM STATUS HISTORY    migration 038   ║
╚═══════════════════════════════════════════════════════════╝
pins.claim_status is a single varchar with no history. stage_transitions
records pipelineStage only — a different vocabulary. Claim status changes
therefore cannot be reconstructed retroactively; they must be logged going
forward.

1a. Migration 038 (verify 038 is free), new table claim_status_history:
      id                  varchar PK gen_random_uuid()
      company_id          varchar NOT NULL REFERENCES companies(id)
      pin_id              varchar NOT NULL REFERENCES pins(id) ON DELETE CASCADE
      from_status         varchar NULL      -- null on first set
      to_status           varchar NOT NULL
      changed_by_user_id  varchar NOT NULL REFERENCES users(id)
      created_at          timestamptz NOT NULL DEFAULT now()
    Index on (company_id, created_at).

1b. Write a row whenever claim_status changes, in the SAME TRANSACTION as the
    pins update. The write path is PATCH /pins/:pinId/insurance — find it and
    confirm that is the only path that can change claim_status. If any other
    endpoint can, report it rather than patching one and leaving the other.

1c. Do NOT backfill. There is no prior history to recover, and inventing one
    from current values would fabricate timestamps. The feed starts empty for
    this event type and fills as statuses change — say so in the UI empty state
    rather than making it look broken.
