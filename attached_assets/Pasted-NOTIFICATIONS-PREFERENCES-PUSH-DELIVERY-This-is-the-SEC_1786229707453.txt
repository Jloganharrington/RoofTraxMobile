DESIGN — read before building
═══════════════════════════════════════════════════════════
FREQUENCY: there is NO scheduler in this repo — no cron, no job queue,
nothing in deps. Immediate sends work today; digests need infrastructure
that does not exist. Store all four values (immediate | daily | weekly |
off) so no migration is needed later, but implement ONLY immediate and off
in v1. Do NOT improvise a setInterval in the API process — it double-sends
on multiple instances and loses its schedule on restart.

Digests are an email concept. Push is immediate-or-off; frequency applies
to email only.

CHANNELS: email and push are independent per notification type. A user may
want a signed contract by email (searchable later) and an overdue item by
push (interrupts them in a truck).

      MONEY     payment_recorded            managers

1b. Migration 039 (verify 039 is free), table notification_preferences:
      id, company_id, user_id (FK users), notification_type varchar,
      email_enabled boolean NOT NULL,
      push_enabled  boolean NOT NULL,
      frequency     varchar NOT NULL DEFAULT 'immediate',
      created_at / updated_at
      UNIQUE (user_id, notification_type)

    Do NOT seed a row per user per type. Absence of a row means "use the

    no target-user parameter of any kind.
    Filter the catalog SERVER-SIDE by role. A field_rep must not receive a
    list containing change_order_pending_approval; do not return everything
    and hide rows in the client.

║ STEP 3 [LOCKED] — DISPATCH LAYER + EMAIL                  ║
╚═══════════════════════════════════════════════════════════╝
3a. ONE dispatch module. Every notification in the system goes through it.
    Signature roughly:
      notify({ type, companyId, pinId?, inspectionId?, actorUserId?, payload })
    It resolves recipients from the catalog's recipientRule, loads each
    recipient's preferences (falling back to catalog defaults), and sends on
    the enabled channels.

    NEVER send a notification from a route handler directly. Two send paths
    means two places to fix when a rule changes — this repo has been bitten
    by exactly that pattern more than once.

3b. Recipient resolution rules:
      assignee                 inspections.inspector_user_id /
                               pins.appointment_assigned_to
      lead_owner               pins.user_id
      managers                 every manager+ in the company
      lead_owner_and_managers  union, deduplicated
    NEVER notify the actor about their own action. Someone who just recorded
    a payment does not need an email telling them they recorded a payment.

3c. Email via the existing per-user SMTP. If a recipient has no SMTP
    configured, skip silently and log — do not fail the originating request.
    A notification failure must NEVER roll back or break the business action
    that triggered it. Dispatch is fire-and-forget relative to the
    transaction.

3d. Wire the first four event sites: payment recorded, contract signed,
    change order pending approval, claim status changed. Do NOT wire all
    sixteen yet — prove the layer works, then fan out.

   - deliberately break the mailer → the business action still succeeds
