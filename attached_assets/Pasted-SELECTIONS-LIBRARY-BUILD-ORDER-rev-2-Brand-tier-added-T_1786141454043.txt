CONTEXT — why this is shaped the way it is
═══════════════════════════════════════════════════════════
Selections split into two kinds with different contractual weight:

  TIER selection is PRICE-BEARING. Choosing a premium product over the
  insurance-covered base creates a betterment the homeowner pays. This feeds
  pins.betterments_amount_cents and the contract price.

  OPTION selection (colour/finish) carries NO price. It's an operational
  detail for the material order and can be decided after contract signature
  without a change order.

Reference prototype (hardcoded — do NOT copy its structure):
github.com/Jloganharrington/Responsive-Builder → artifacts/nuhome-portal.
Three siding tiers, ~70 colours in five groups, per-tier availability. The
shape is right; the hardcoding is what this replaces.

1a [LOCKED] Five tables in data-migrations/033_selections_library.sql plus
Drizzle schema in lib/db/src/schema/rooftrax.ts (verify 033 is free).
All company-scoped, varchar PK gen_random_uuid(), created_at/updated_at
timestamptz, and is_active boolean NOT NULL DEFAULT true.

  selection_categories
      company_id, name, slug, sort_order, is_active
      Seed each company with: Roofing, Siding, Gutters, Interior.
      Company-configurable — do NOT hardcode as an enum.

  selection_brands                                        ← NEW LEVEL
      company_id, category_id FK, name, logo_path text NULL,
      sort_order, is_active
      A brand belongs to exactly one category. "Mastic" under Siding and
      "Mastic" under Roofing are two rows — manufacturers' product lines and
      colour palettes differ by category, and sharing the row would blend
      palettes that don't belong together.
      A "Generic" or "Builder Grade" brand is a normal thing to create for
      unbranded base material.

  selection_products          (the TIERS — price-bearing)
      company_id, category_id FK, brand_id FK NOT NULL,
      name, description text, specs jsonb,
      is_base boolean NOT NULL DEFAULT false,
      price_delta_cents integer NOT NULL DEFAULT 0,   ← PER UNIT
      unit varchar NOT NULL,                          ← "per square", "per LF"
      sort_order, is_active

      PRICING IS PER UNIT. price_delta_cents is the delta per unit above the
      category's base product. Contract Builder multiplies by job quantity.
      A flat total would be wrong across differing job sizes — the reference
      prototype's flat figures worked only because it was one specific house.

      ⚠ is_base IS SCOPED TO CATEGORY, NOT BRAND. There is exactly one
      insurance-covered product per category, and every product in that
      category — across all brands — prices its delta relative to it.
      Partial unique index:
        CREATE UNIQUE INDEX ... ON selection_products (company_id, category_id)
          WHERE is_base = true AND is_active = true;
      The base product MUST have price_delta_cents = 0 — enforce server-side.
      Setting a new base clears the old one IN THE SAME TRANSACTION. Do not
      surface a constraint violation the user has to untangle manually.

  selection_options           (the COLOURS — no price)
      company_id, brand_id FK NOT NULL,                ← BRAND, not category
      name, option_group varchar NULL   ("Light", "Deep", "Cedar Colors"),
      swatch_hex varchar NULL,          #RRGGBB
      swatch_image_path text NULL,      object storage; textures/woodgrain
      hoa_compliant boolean NULL,       tri-state: true / false / unknown
      sort_order, is_active
      At least one of swatch_hex or swatch_image_path required — validate
      server-side.
      Options attach to BRAND because colour palettes are published per
      manufacturer.

  selection_product_options   (which colours are on which tier)
      company_id, product_id FK, option_id FK
      UNIQUE (product_id, option_id)
      ⚠ VALIDATE that the option's brand_id matches the product's brand_id.
      A CertainTeed colour must never be mappable onto a Mastic product.
      Reject with 400, do not silently allow it.

1b [LOCKED] Soft-delete only — is_active = false, never DELETE, on brands,
products, and options. Once a selection lands on a signed contract the record
must remain resolvable forever; an audit trail that can lose its referents is
not an audit trail. Hard DELETE only when nothing references the row —
verify first, 409 otherwise.
Deactivating a brand must deactivate or hide its products and options
consistently. State how you handled the cascade.

1c [LOCKED] API, openapi-first then regenerate. Full CRUD on all five tables,
company-scoped. ADMIN+ for every WRITE (same gate as Templates and Price
Book — this is company configuration).
READS are open to any authenticated user: the Portal will need them and reps
benefit from seeing what's offered. Do not gate reads to admin.
Swatch and brand-logo uploads reuse the EXISTING presigned-upload +
object_ownership flow. Do not write a new upload path.
